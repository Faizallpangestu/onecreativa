# M3.1 — Real invoice email delivery

Implementation in the working tree; no production configuration, database migration, commit, push, or real-recipient test performed. Finance sends **existing official billing invoices**. BE-01–BE-03 creation, pricing, enrollment, charge, bank master, and payment validation remain in force.

## Behavior and source of truth

- PHP uses the existing bundled PHPMailer and `salary_mail_config()` / shared SMTP transport. Salary email behavior is preserved.
- Recipient comes only from `billing_invoices.email`. Client recipient, price, bank, and document URL overrides are ignored. Sending does not create an invoice, generate a new invoice number, reprice, update payments, or update payment status.
- Saved number, program, amount, terms, due date, and bank snapshot are used. Missing recipient/token/term schedule/bank snapshot fails explicitly; legacy records do not receive guessed bank values, full-payment schedules or enrollment backfills.
- `invoice_document.php` now retains the exact saved bank holder, removing its old holder substitution and hardcoded fallback. Historical reads remain available; incomplete historical snapshots need Finance reconciliation before email.
- `automation_logs` is the single email-attempt source, with `stage=invoice_email`, `channel=Email`. No second delivery table, email queue, or synthetic `billing_terkirim`/read/payment rows are created.
- Each attempt is committed as **Pending** with an audit entry before rendering/SMTP. The same row becomes **SMTP Accepted** only after final SMTP DATA acceptance for the configured recipient and CC, or **Failed** with a sanitized reason. Earlier attempts remain intact. SMTP acceptance does not prove inbox arrival or reading.
- Recipient/CC addresses and small attempt metadata are logged; MIME bodies, token URLs, credentials, SMTP debug transcripts and raw server replies are not.
- A per-invoice database advisory lock serializes send/resend. A stable `request_id` replays the stored result, including its original error status. `previous_attempt_id` prevents another newly generated request from bypassing concurrent/stale resend confirmation.
- A crash after Pending, a lost final SMTP reply, partial recipient acceptance, or a failure to save the SMTP result requires operator reconciliation. Pending/uncertain attempts block a fresh send. SMTP has no transactional exactly-once guarantee; this implementation does not claim one.

## API contract

Both endpoints use the existing session authorization. POST requires Finance `prepare` permission and `X-CSRF-Token`.

```http
POST /api/billing.php
Content-Type: application/json
X-CSRF-Token: <session token>
```

```json
{
  "action": "send_invoice_email",
  "invoice_id": "<existing persisted invoice number>",
  "request_id": "<stable 8–100 character alphanumeric/hyphen/underscore key>",
  "previous_attempt_id": null
}
```

For an explicit resend, `previous_attempt_id` must equal the latest attempt ID confirmed by the user. A network retry uses the **same complete request**, not a new key or invoice. First inspect:

```http
GET /api/billing.php?view=email_attempts&invoice_id=<existing number>
```

Response: `{ "status": "success", "data": { "attempts": [...] } }`, newest first. The normal Finance GET adds `data.email_attempts` (latest 500 email attempts) and each invoice's `email_delivery` (its actual latest attempt, independent of that limit). Full per-invoice history is available through the dedicated GET.

Successful POST: HTTP 200, `status=success`, `data.attempt.status="SMTP Accepted"`, `data.replayed`, and `data.http_code`. Attempt fields include `id`, `invoice_id`, `request_id`, `recipient`, `cc`, `created_at`, `completed_at`, `pdf_attached`, `error_message`, and `delivery_uncertain`. A failed attempt returns the same envelope with `status=error` and useful `message` / `data.attempt`.

| HTTP | Meaning |
| --- | --- |
| 200 | SMTP accepted, or replay of that accepted attempt |
| 401 / 403 | Login / permission / CSRF failure; no send |
| 404 | Invoice absent |
| 422 | Invalid request, saved email/amount, or ineligible invoice status |
| 409 | Configuration/snapshot dependency, concurrent/stale request, or unresolved Pending/uncertain send |
| 502 | Required PDF render failure or SMTP rejection/transport failure; inspect attempt |
| 500 | Database/audit failure before sending; pre-send transaction rolls back |

The automation callback refuses the reserved `invoice_email` stage; an n8n payload cannot create PHP SMTP acceptance evidence.

## Private SMTP and CC configuration

Use the existing private `backend/config/mail.local.php` (not committed or included in builds), based on `mail.example.php`. Keep the existing SMTP host/port/encryption/username/password/from values used by salary mail. Do not create a separate credential file.

| Key | Value / responsibility |
| --- | --- |
| `host`, `port`, `encryption` | Existing SMTP server; `tls` STARTTLS or `ssl` implicit TLS |
| `username`, `password` | Existing private provider credentials |
| `from_email`, `from_name` | Provider-authorized sender and Finance name |
| `ca_file` | Optional trusted CA bundle, certificate verification remains enabled |
| `invoice_email_sender` | Empty disables this feature (default); set `php` only after active n8n invoice email is disabled; `n8n` also blocks PHP |
| `invoice_cc_tiffa` | Empty placeholder until Finance supplies Bu Tiffa's verified email |
| `invoice_cc_alfin` | Empty placeholder until Finance supplies Pak Alfin's verified email |
| `invoice_api_base_url` | Official public HTTPS API base, without trailing slash/query, e.g. `https://your-domain/api`; local HTTP allowed only for local fixtures |
| `invoice_pdf_worker_url` | Existing private Playwright worker base |
| `invoice_pdf_worker_secret` | Private value matching the worker's `WORKER_SECRET` |
| `invoice_pdf_required` | Boolean true by default. False explicitly permits a link-only email if the PDF worker is absent/unavailable |

Environment overrides use the existing prefix, e.g. `CREATIVA_SMTP_HOST`, `CREATIVA_SMTP_INVOICE_EMAIL_SENDER`, `CREATIVA_SMTP_INVOICE_CC_TIFFA`, `CREATIVA_SMTP_INVOICE_CC_ALFIN`, `CREATIVA_SMTP_INVOICE_PDF_REQUIRED=true`. CC supports one address per named key, deduplicates them and the main recipient, and fails on a nonempty invalid address. Actual addresses have not been supplied and are not invented.

The PHP host needs existing mysqli/OpenSSL/mbstring plus cURL, outbound SMTP connectivity, a trusted CA store, access to the worker, and execution time sufficient for PDF + synchronous SMTP. The existing `automation_logs` and accounting audit schema must be available. No new table/migration is needed. The Finance GET already provisions the repository's existing automation log table; the send action itself refuses an unavailable history schema.

## PDF worker

Use the existing `automation` package and lockfile:

```sh
npm ci --prefix automation
npm run install-browser --prefix automation
npm start --prefix automation
```

Configure existing worker `PORT`, `WORKER_SECRET`, `ALLOWED_RENDER_ORIGINS` for the official document origin. Optional `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` uses an installed compatible Chromium/Chrome (used by local tests). Never expose the worker secret to the browser. The worker must reach the tokenized official document URL.

PHP requests `/render-invoice-pdf?format=binary`, validates HTTP status, PDF MIME, `%PDF-` signature, EOF marker, and size before attaching bytes. The worker now rejects unsuccessful document HTTP responses and sanitizes render errors to avoid logging token URLs. No browser jsPDF or HTML-renamed-PDF artifact is used. A required missing/failed PDF prevents SMTP entirely.

## Controlled Gmail inbox acceptance procedure (operator, not run here)

1. Use an isolated staging database with one already persisted official test invoice whose saved recipient is an inbox you control. Do not change a real student's invoice/recipient for testing. Use its original saved amount, terms, token and complete bank snapshot.
2. Disable other senders, leave CC placeholders empty initially, and configure the existing private SMTP sender. For Gmail use `smtp.gmail.com`, `587` + `tls` or `465` + `ssl`. Use an App Password only if permitted for the account; never put the normal account password in the repository. This transport reuses SMTP AUTH; OAuth onboarding is not part of M3.1.
3. Configure the public staging document base and local/private worker, keep PDF required, and verify the document renders before sending.
4. Log in as Finance; check the saved email shown in Invoice & Penagihan. Click **Kirim Email**, confirm, and wait for **SMTP Accepted**. Open server attempt history; verify one accepted attempt, expected recipient, PDF attachment flag, and unchanged invoice/payment status.
5. Inspect the controlled inbox/spam folder, open the actual PDF, verify number/program/amount/terms/bank snapshot and document link. This is the outstanding real-provider acceptance check, not implied by local capture tests.
6. After Finance supplies approved CC addresses, add the private keys and deliberately resend the same invoice after confirmation. Verify a second preserved attempt and expected CC; do not fabricate CC addresses. For staging CC testing use only explicitly controlled inboxes.
7. For an uncertain response, inspect history with the same request key first. Never generate a new invoice or blindly repeat SMTP. Pending/uncertain recovery requires SMTP/provider evidence and Finance/DB PIC sign-off; only after proof of non-submission may the operator correct that specific attempt's reconciliation state (retain attempt, request key, reason and audit evidence). No bulk deletion or automatic expiry is provided.

Gmail source references: [Google SMTP endpoints](https://developers.google.com/workspace/gmail/imap/imap-smtp), [Google App Password requirements and account restrictions](https://support.google.com/accounts/answer/185833?hl=en). Provider policy may require an alternative configured SMTP relay.
