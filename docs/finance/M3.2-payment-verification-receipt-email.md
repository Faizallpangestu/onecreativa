# M3.2 — Payment verification, official receipt PDF and email

M3.2 baseline `6f0790d` has been committed and pushed on `feat/backend-finance-workflow` (built on M3.1 `da362d4`). M3.2.1 changes remain in the working tree; this bugfix does not commit, push, deploy, configure production, or send real email.

## Actual payment sources

| Source | Existing meaning | M3.2 behavior |
| --- | --- | --- |
| `billing_pembayaran` | Billing payments; `Menunggu`/`pending` is unverified, `Terverifikasi`/`verified` is verified | Verify by exact `payment_id`, update that row, preserve its proof |
| `student_payment_submissions` | Portal uploads: amount, transfer date/reference, private proof file, student and invoice-link IDs; status `pending`/`accepted`/`rejected` | Finance reviews the exact submission; creates/reuses its explicitly linked billing payment once, then verifies that payment |
| Accounting review of a submission | Existing `accepted` requires a real posted/verified allocated `accounting_transactions` record and its `transaction_id` | Preserved. Billing verification does not fabricate that ledger transaction or mark the submission accounting-accepted |
| Direct Finance `approve_payment` | An intentional new manual verified payment, previously inserted by the Finance adjustment form | Preserved as a distinct workflow with a stable request key; uses the same receipt/PDF/email completion |

Portal upload is **not** a `billing_pembayaran` INSERT. `sb_submit()` stores a separate persisted review request and a private `student_payments/<random filename>` document. Its original records/files and accounting review contract remain intact. The Finance page displays unmapped submissions separately from billing payments, with their real submission ID, amount/date/reference, evidence link, and accounting review status.

The smallest bridge reuses **existing `accounting_idempotency`**, without new tables or migrations. A reserved `billing-submission-<submission_id>` key with `operation=billing_submission` stores the exact resulting `payment_id`. Invoice-link ownership and the stored invoice student owner must agree. On first Verify, the saved evidence creates a pending billing row within the transaction and that exact row becomes verified. If one pending billing row already contains the same physical evidence and matching saved amount/date, that row is linked and reused. Multiple matches, a previously verified matching proof, conflicting owners, rejected/accepted ledger-review sources, and unresolved ledger allocations require reconciliation; names, email and approximate amounts are never identities.

The original submission may therefore still show accounting `pending` while its linked billing payment is Verified. This is an explicit separation of the existing ledger review and billing state, not a fabricated accounting approval. Portal/accounting balance views that use posted allocations still require the existing Finance accounting process. `invoice_client` submissions and ambiguous historical ledger-only payments are not silently converted into official billing receipts.

## Verification lifecycle

1. Finance opens evidence and confirms **Verify** for a saved payment or identified student submission.
2. The server requires the existing Finance `prepare` permission, authenticated session and CSRF token.
3. Within a database transaction, existing idempotency/actor locks and the invoice/payment locks protect the exact records. The server derives amount/date/method from the pending row, checks proof availability, duplicate evidence and invoice ownership, and checks actual verified amounts against outstanding.
4. The same pending payment becomes `Terverifikasi`; no duplicate INSERT is used for an existing payment. Invoice status becomes Paid or Partially Paid using exact integer cents/decimal helpers. Client remaining balance, receipt number and verification status are ignored.
5. A verification audit entry stores the receipt snapshot, and the stable request result is saved in `accounting_idempotency` with `operation=billing_verify_payment` or `billing_manual_payment`. The transaction commits.
6. Only after commit does the server generate/cache the PDF and attempt receipt email. Rendering/SMTP failure does not reverse verification. The HTTP verification response remains successful and includes independent payment, receipt, PDF and email states.
7. A replay returns the existing payment/receipt. Automatic delivery uses `receipt-auto-<payment_id>` and the existing receipt history; Verify replay never resends a failed/uncertain email. A separate confirmed email-only resend is available.

Manual Finance recording still creates a new payment as explicitly authorized by that form; it is not represented as review of an existing upload. A manual request containing `payment_id` or `submission_id` is rejected. Its new `request_id` is mandatory to prevent lost-response/double-click duplication. All in-repository `approve_payment` callers were checked; the Finance form is the caller and was updated.

Real SQL concurrency exposed a deadlock between invoice locking and missing-key gap locks in the existing idempotency helper. `bp_atomic()` reuses `ac_atomic()` rollback and retries **only the database transaction**, at most three times for MySQL 1213. Exhausted deadlock or conflicting unique key returns 409; existing 1205 rollback/conventions remain. PDF/SMTP are outside this retry loop. Database audit failure rolls back verification before external work.

For invoices with existing ledger allocations, a new billing recognition is allowed only when those allocations are provably linked to the matching verified `billing_payment` records and amounts. Unknown ledger-to-billing relationships require reconciliation rather than counting the same money twice. Identical saved proof bytes cannot be recognized as distinct payments without reconciliation. A bank statement covering multiple legitimate payments needs Finance review; new request keys cannot bypass the duplicate-evidence guard.

## Receipt identity and official PDF

- One real verified `billing_pembayaran.id` produces one receipt: existing `RCT-YYMM-XXXX` convention, based on saved transfer date and padded payment ID. Padding is a minimum width; payment IDs remain the identity. Resend does not allocate a new number.
- New verification stores immutable receipt values in the existing verification audit: payment/invoice IDs, receipt number, customer, amount, date, method, invoice total, cumulative verified amount, remaining balance, status, and included verified payment IDs.
- A first official PDF/email for a historical verified row freezes actual saved verified totals under invoice/payment locks, with a separate `receipt_snapshot` audit entry. Historical payment amounts/status/proofs are not rewritten. Earlier undocumented historical receipt totals are not guessed.
- The existing `receipt_document.php` A4 layout is reused. Its exact `payment_id` route rejects unverified rows. All numeric calculations/formatting use exact cents/decimal strings, including sen and a zero remaining balance. A partial receipt retains its snapshot when another payment is later verified.
- The historical invoice-only Paid display fallback remains available for legacy viewing. It is never a source for official receipt email/PDF preparation: those paths require a real verified payment ID.
- The existing `/render-receipt-pdf?format=binary` worker renders the exact payment URL. M3.1 MIME/signature/EOF/size validation is reused. A receipt email **always requires a real PDF**, even when optional link-only invoice email is configured.
- PDF bytes are archived privately under the existing private document root, `receipt_pdfs/receipt-<payment_id>-<snapshot hash>.pdf`, using a temporary write and rename. This is a document artifact/cache, not a second payment/attempt source. CC changes/resends reuse the same snapshot/file. No browser jsPDF or HTML renamed as PDF is used.
- The authenticated PDF endpoint serves the archived file or renders that same receipt on demand. A failed worker leaves the committed verified payment and official HTML receipt available; PDF generation can be retried independently.

Verified payments and invoices that carry verified receipts cannot be deleted through the Finance deletion routes. This is an intentional retention guard. Historical correction/cancellation/reconciliation is not implemented by deleting payment evidence in this task.

## API contracts

All routes reuse `/api/billing.php`. POST requires session, Finance `prepare`, and `X-CSRF-Token`; GET uses the existing Finance read permission.

### Verify an existing pending billing payment

```json
{
  "action": "verify_payment",
  "invoice_id": "<stored invoice ID>",
  "payment_id": 123,
  "request_id": "<stable retry key>"
}
```

For an existing portal proof not yet mapped, replace `payment_id` with authoritative `submission_id`. Supply exactly one. This is an explicit source bridge; the response returns its real `payment_id`. Subsequent requests for that submission resolve to the same payment. No registration/student identity migration is performed.

### Preserve manual Finance recording

`action=approve_payment` retains its amount/date/method and optional multipart `proof` fields, and now requires `request_id`. The authenticated actor is the verifier; client approver names/status/remaining balances are not authority. The form reconciles uncertain responses with the same key before retrying.

### Verify/manual response

```json
{
  "status": "success",
  "data": {
    "payment_id": 123,
    "invoice_id": "<stored invoice ID>",
    "payment_status": "Verified",
    "receipt_status": "Available",
    "receipt_number": "RCT-2611-0123",
    "receipt_url": "<official HTML document URL>",
    "receipt_pdf_url": "/api/billing.php?view=receipt_pdf&payment_id=123",
    "pdf_status": "Available",
    "status": "Partially Paid",
    "terbayar": "300.10",
    "sisa": "700.15",
    "verified_now": true,
    "replayed": false,
    "email_status": "Failed",
    "email": { "attempt": { "id": 456, "payment_id": 123, "status": "Failed" } }
  }
}
```

Amounts/numbers above illustrate the response shape, not Finance pricing policy. Email error details are available on the attempt. Verification returns HTTP 200 once committed, even when PDF/SMTP fails. `receipt_status=Available` describes the official receipt document/identity; `pdf_status=Available|Not Generated` separately describes the server PDF. `email_status=Not Attempted` means no attempt exists; attempts themselves use only Pending / SMTP Accepted / Failed. A post-commit failure preserves payment verification. Email state follows persisted attempts; if history is unavailable, status is null with `email.history_available=false` rather than fabricated Pending.

Existing response fields `invoice_url`, `status_url`, `proof_url`, `proof_mime` and `rpa_dispatched` remain available. Normal Finance GET enriches each verified payment with `receipt` metadata and includes separate `student_submissions`, with `billing_payment_id` where mapped. GET performs no automatic email send.

```http
GET /api/billing.php?view=payment_request&request_id=<stable verification/manual key>
```

Returns `data.payment` with the committed result, or null after a successful lookup proving no result currently exists. It is scoped to the authenticated actor and the payment operations. Failed/unavailable lookup is not evidence that payment was absent. Browser requests retain their stable key while uncertain.

### Send/resend only an existing verified receipt

```json
{
  "action": "send_receipt_email",
  "payment_id": 123,
  "request_id": "<stable email request key>",
  "previous_attempt_id": null
}
```

```http
GET /api/billing.php?view=receipt_email_attempts&payment_id=123
GET /api/billing.php?view=receipt_pdf&payment_id=123
```

Email responses follow M3.1: HTTP 200 means SMTP accepted submission (including configured CC), not inbox arrival or reading. Failed send returns 409 for configuration/stale history/Pending conflict, or 502 for required rendering/SMTP failure. Bad IDs/payload/status/proof use 404/422/409 as applicable; permission/session/CSRF use 401/403. Sending cannot verify or insert a payment.

History is newest first, filtered by **payment_id**, `stage=receipt_email`, `channel=Email`. Each attempt records invoice/payment/receipt identity, request and previous-attempt keys, actor, recipient/CC, Pending/SMTP Accepted/Failed, created/completed time, sanitized error and uncertainty. `pdf_generated` distinguishes a generated document from `pdf_attached` on a constructed email; a configuration failure does not claim an attachment was submitted. Per-receipt named locks, stable request replay and previous-attempt comparison prevent duplicate submissions. Pending/uncertain/partial SMTP acceptance blocks blind retry. The `invoice_email` stage and invoice email UI remain separate. The n8n callback cannot write either reserved PHP SMTP evidence stage.
